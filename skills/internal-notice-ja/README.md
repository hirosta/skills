# internal-notice-ja

日本の会社の社内のお知らせ・週報・連絡を、読み手と転送先に合わせて作成・修正するスキルです。件名で用件と日時を示し、本文の最初の3行で結論と必要な行動を伝えます。文案と要確認事項、転送情報の点検結果を返します。

## 扱う種類

| 種類 | 主な読み手 | 型の重点 |
| --- | --- | --- |
| 全社へのお知らせ | 全社員 | 対象と対象外、変更内容、開始日、必要な作業 |
| 週報・進捗の報告 | 上長・関係部署 | 予定に対する結論、進捗、相談、来週の予定 |
| 部署内の依頼・連絡 | 部署のメンバー | だれに・何を・いつまで、返信の要否 |
| 障害・事故の報告 | 関係者・上長 | 第一報と続報、確認済みと未確認、次報時刻 |
| よくある質問への回答 | 問い合わせた社員 | 答え、規程の根拠、例外、問い合わせ先 |
| その他の社内連絡 | 依頼に応じる | 共通の決まりだけを使用 |

## 入れ方

スキルを読み込めるAIエージェントで使います。このリポジトリを取得したフォルダーから、`skills/internal-notice-ja/` を導入先のスキル用フォルダーへコピーしてください。同名のフォルダーがある場合は内容を確認し、上書きするか決めてからコピーします。フォルダー内の `LICENSE` も含めます。他のスキルは必須ではありません。

補助スクリプトはPython 3の標準ライブラリだけで動きます。追加の依存は不要です。

## 使い方

```text
internal-notice-jaで、次の架空の依頼メモから部署内の連絡を書いてください。
管理部の備品担当者向けです。2026年11月6日（金）15:00までに
貸出一覧の未返却欄を更新し、管理部窓口へ完了を返信してもらいます。
未返却なしの場合も「なし」と入力します。問い合わせ先は管理部窓口です。
部署外へ転送されても分かる文にしてください。
まず件名と冒頭3行を見せてください。
```

不足する材料だけを質問し、確認できなければ `［要確認：項目］` と残します。件名と冒頭案を利用者に示し、内容が伝わることを確かめてから本文を作ります。通常は会話内で返し、ファイルや設定は確認なしに書き換えません。外部へのアクセス、送信、投稿、削除は行いません。

ローカルの文面を点検する例（リポジトリのルートから実行）：

```bash
python3 skills/internal-notice-ja/scripts/check_notice.py skills/internal-notice-ja/examples/request-before.txt
python3 skills/internal-notice-ja/scripts/check_notice.py skills/internal-notice-ja/examples/request-after.txt
```

入力はUTF-8（BOM付きも可）。空行を除く最初の行を件名、続く3行を本文の冒頭とします。`件名：` は付けても省いても構いません。Markdownの見出しや依頼メモを混ぜず、文面だけを渡します。読み取りと標準出力だけを行い、原文を書き換えません。出力には日付やあいまいな期限の一致文字列が含まれるため、公開先へ貼る前に確認してください。

検出項目は、件名末尾の「について」、件名の日付の欠落、冒頭の日時・依頼表現の欠落、絵文字の候補、あいまいな期限、曜日のない日付、残った「要確認」です。件名と冒頭の欠落は各条件1件、その他は一致ごとに数え、行番号と合計を出します。日付は年月日、月日、スラッシュ・ハイフン形式を対象とし、全角数字も正規化して読みます。曜日は日付直後の括弧付き表記を対象にします。

依頼表現は「ください」「お願いします」「お願いいたします」「願います」「求めます」、返信・対応・作業の「不要」の代表表記を対象にします。期限がない報告は確認時点と返信不要で表せます。検出があっても正常終了は0、引数や入力エラーは2です。引数のエラーも標準出力へ出します。

## 修正前と修正後の比較

すべて同じ架空の材料を使った組です。前の文では情報が後ろにあり、後の文では件名と冒頭へ移しています。日付の年は依頼メモに基づいて補いました。FAQのあいまいな相談時期は、材料にない期限なので削除しました。

| 種類 | 依頼メモ | 修正前 | 修正後 | 決まりに沿って変えた点・保持した情報 |
| --- | --- | --- | --- | --- |
| 全社へのお知らせ | [依頼メモと冒頭案](examples/announcement-memo.md) | [「会議室予約の切り替えについて」](examples/announcement-before.txt) | [「【お知らせ】会議室予約システム切り替え・2026年11月9日（月）」](examples/announcement-after.txt) | 件名に用件・切替日、冒頭に対象・作業・期限・返信先を移した。呼びかけと絵文字を除去。予約しない社員の扱い、切替時刻と期限は維持。 |
| 週報・進捗の報告 | [依頼メモと冒頭案](examples/weekly-memo.md) | [「今週の台帳整備について」](examples/weekly-before.txt) | [「【報告】備品台帳整備の週報・2026年11月2日（月）〜2026年11月6日（金）」](examples/weekly-after.txt) | 冒頭を予定20件に対し18件完了・2件遅れという結論と判断依頼にした。前週累計12件と今週累計30件を同条件で表示。増分18件、期限、来週の順序を維持。 |

| 障害・事故の報告 | [依頼メモと冒頭案](examples/incident-memo.md) | [「社外秘・予約システムの障害について」](examples/incident-before.txt) | [「【報告】【社外秘】会議室予約の登録不可・第一報・2026年11月5日（木）10:15時点」](examples/incident-after.txt) | 登録不可と依頼・次報時刻を冒頭に移動。8人は申告人数として維持し、全体の影響範囲・原因・復旧見込みは未確認と明記。社外秘表示も維持。 |
| よくある質問への回答 | [依頼メモと冒頭案](examples/faq-memo.md) | [「貸出機器の延長について」](examples/faq-before.txt) | [「【回答】貸出機器は原則延長不可・2026年11月6日（金）回答」](examples/faq-after.txt) | 可否と再申請を冒頭に置いた。規程名・第4項・修理代替機だけの例外は維持。材料にない相談期限は作らず「あいまいな期限」を削除。 |

## 試した結果

条件：GPT-6（Codex）が、架空会社「星こばこ備品」の依頼メモを5種類各1本作り、共通の決まりと各型を読んで件名・冒頭案、本文を作成しました。修正前後の計10ファイルを同じモデルが照合し、`check_notice.py` を実行しました。実在の会社・人物・規程・業務記録は使っていません。

依頼メモと提示用の件名・冒頭案は上表のリンクに記録しました。これは同じモデルによる作成・照合で、実際の利用者への提示と確認応答の往復は未実施です。本文は検証用に作成したもので、実利用者の承認済み文面ではありません。

| 種類 | check_notice.py 修正前 → 修正後 | 修正後に残った要確認 | ai-smell-ja 修正後 |
| --- | --- | --- | --- |
| 全社へのお知らせ | 8件 → 0件 | なし | 0件 |
| 週報・進捗の報告 | 9件 → 0件 | なし | 0件 |
| 部署内の依頼・連絡 | 6件 → 0件 | なし | 0件 |
| 障害・事故の第一報 | 7件 → 0件 | なし | 0件 |
| よくある質問への回答 | 6件 → 0件 | なし | 0件 |

修正後の5本すべてで `直すべき点 0件` と、人が確かめる点の案内が表示されました。これらの件数は、上記の検出項目の一致数であり、読みやすさの評価点ではありません。

どの依頼メモにも用件・対象・日時・行動・問い合わせ先があり、未提供情報を推測で埋める必要はありませんでした。障害の原因・復旧見込みは「未確認」の事実として残し、「要確認」の未入力欄とは区別しました。日付と曜日は暦で照合しました。

補助スクリプトはPython 3で構文と字下げを確認し、標準ライブラリだけのインポートであることを確認しました。<一時領域>で、空文面、要確認の残り、BOM付き・全角日付、絵文字（顔・旗・キーキャップ）、不正な文字コード、引数なし、存在しない入力、ディレクトリ指定、ヘルプを手動確認しました。入力エラーは終了値2で標準出力だけに案内が出ました。型に載せた障害の続報例も0件でした。自動テスト・テストスイートは作成していません。

5本の修正後文について、利用可能な `ai-smell-ja` の手順とパターン一覧でも点検し、材料の数字・期限・対象・否定・依頼の強さを照合しました。敬語は全社・部署内では「ください」、上長には判断の依頼、FAQには回答を先に置く形です。社外秘情報の詳細・個人評価・健康情報・未確定人事を含めず、障害報告は社外秘表示と転送禁止を維持しました。いずれも同じモデルによる確認です。

## 分かっていないこと・制約

- 実際の社員による読みやすさの評価、業種・会社による慣習の違いは確認していません。時間短縮や品質向上を測定・保証していません。
- 5種類各1本の短い架空の例だけです。長文、複数の依頼、実際の第一報から続報への運用は未評価です。
- 正規表現の指摘には見逃しと誤検出があります。「まで」があるだけでは期限として数えず、日時の存在だけで判定します。絵文字の全種類、あいまいな表現の全活用を網羅しません。引用や名称に含まれる文字も拾います。
- 0件でも、対象者の妥当性、結論、敬語、転送の安全性、日付と曜日の一致、規程の内容・法令上の適法性は保証しません。最終行に人が確かめる点を表示します。
- 日付・数字・規程名・担当者の未確認を補作しません。法令判断や人事・健康情報の扱いが必要なら担当部署に確認します。「社外秘」の表示だけで情報の共有が安全になるわけではありません。
